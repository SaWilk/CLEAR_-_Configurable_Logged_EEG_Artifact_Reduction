This is a step-by-step guide to setting up the config script for your analyses.

The Pipeline is set up in a way that you only need to run the function run_eeg_pipeline(), through which you pass your config-file and optionally specific subjects.

______________________________
FIRST THINGS FIRST: if you rename the config file, you also Need to Change the function name at the top of the script.

______________________________
PROJECT AND MACHINE PROFILE(S):
define your project and analysis Environment (i.e. "profiles")

Project-identity:
- The pipeline name should be recognisable for you and will appear in the log headers
- The step-prefix is requiered to find the correct step-functions (only Change if you also Change the step function file names)
- The masterlog prefix will be the start of your logfile name- make it succinct and informative.
- The cfg.bids labels define the Output names of files and directory structure of the bids conversion in prep01

Profiles:
- profiles refer to analysis Environments (our defaults are pc, server_windows and hpc)
- you only need to set paths that you will use, e.g. if you have the raw data on your local machine and will do the bids-conversion only there but the rest of the pipeline on the high performance cluster (hpc), you can leave 'source*_root' empty
- you can set override paths in the same section, e.g. if you are testing the pipeline on a subject that is not saved in your profile_path

Toolbox-paths:
- tell the Pipeline where to find the required toolboxes for each profile

______________________________
GLOBAL SETTINGS:

Overwrite behaviour: 
- "delete" replaces output files if they already exist
- "skip" checks if output for step-function exists already and skips the respective analysis step
- "if_older_than" checks creation date of existing Output files and only replaces older ones, requires cutoff date.

Constants:
- defines which sub-IDs are recognized (default: 3-digits), as well as log-file names
- sets the Location where logs are saved (default: creates log Folder alongside step-function outputs)

Subjects:
- specify explicit subject list and/or minimum sub-ID
- leave empty for pipeline to automatically pull subjects from root-directories

Parallel:
- run several subjects in parallel (Default: true); "scrambles" command line output so not recommended for Troubleshooting
- you can set a specific number how many analyses should run in parallel, or let the Pipeline determine available ressources automatically (recommended).

______________________________
STEP SETTINGS:

Step toggles: 
- set 'run' true for each preprocessing step you want to run
- set 'overwrite_mode' for each step individually, if you want to deviate from global Setting. Otherwise leave empty ("")
- Note: by default, if you rerun intermediate steps (i.e., if output files already exist), subsequent steps will be toggled to run. This prevents inconsistent Outputs. If you want to only rerun one step (e.g. for Troubleshooting) set cfg.steps.enable_downstream_rerun = false

------------------------------
STEP 01: BIDS FORMATTING
- set which data (eeg/bahav) to copy and optional EEGLAB export functions, defaults work 
- define regexp Patterns for raw filenames, so Pipeline can find datafiles. !! IF THIS IS NOT CORRECT THE PIPELINE CANNOT RUN !!
- raw_eeg_regex sets the pattern prep01 Looks for to copy data into BIDS conforming file structure
- existing_bids_vhdr_regex sets the filename pattern the function looks for if files were not re-organized by Pipeline

------------------------------
STEP 02: TRIGGERFIX
Enable cfg.steps.prep_02_triggerfix.run in eeg_pipeline_config.m and edit
the existing cfg.paradigms.myParadigm.triggerfix section. Step 02 reads BIDS
BrainVision files using cfg.bids.task_label and cfg.bids.session_label by
default. Override input_vhdr_pattern only if the filenames differ. If a session
has several headers, allow_multiple_runs processes all of them. Otherwise
multiple_vhdr_policy selects the most recent by default and also supports
"first" and "error". Set use_explicit_chanlist to true to read only the channels
in explicit_chanlist. The step saves *_triggersfixed.set files for Step 03.

Enter the codes as they were recorded in raw_triggers. In blocking, give each
trigger category a raw_key referring to one of those entries. The blocks list
assigns a new code to successive occurrences in that category. For example,
n=4 takes four occurrences and n=Inf takes the remainder. Use an empty code
("") to count a block while keeping its original labels.

Example without phases. Fill these fields to rename the first four occurrences
of S 11 to S 111 and all later occurrences to S 112.

    cfg.paradigms.myParadigm.triggerfix.use_gating_from_start_markers = false;
    cfg.paradigms.myParadigm.triggerfix.raw_triggers.rawA = "S 11";
    cfg.paradigms.myParadigm.triggerfix.blocking.categoryA.raw_key = "rawA";
    cfg.paradigms.myParadigm.triggerfix.blocking.categoryA.blocks = { ...
        struct('n', 4, 'code', "S 111"), struct('n', Inf, 'code', "S 112")};

Example with phases. Give each phase its own start marker. All category counts
restart at every observed marker. Phase and category names are MATLAB struct
field names and must match across settings. Use .code for one label or
.blocks for a list of blocks in a phase. Categories without a phase override
use the blocks defined under blocking.

    cfg.paradigms.myParadigm.triggerfix.use_gating_from_start_markers = true;
    cfg.paradigms.myParadigm.triggerfix.gates.start_markers = ...
        struct('phase1', "S 81", 'phase2', "S 82");
    cfg.paradigms.myParadigm.triggerfix.raw_triggers.rawA = "S 31";
    cfg.paradigms.myParadigm.triggerfix.blocking.categoryA.raw_key = "rawA";
    cfg.paradigms.myParadigm.triggerfix.phase_specific_trigger_renaming = true;
    cfg.paradigms.myParadigm.triggerfix.phase_specific_trigger_renaming_rules.phase1.categoryA.blocks = { ...
        struct('n', 2, 'code', "S 311"), struct('n', Inf, 'code', "S 312")};
    cfg.paradigms.myParadigm.triggerfix.phase_specific_trigger_renaming_rules.phase2.categoryA.blocks = { ...
        struct('n', 1, 'code', "S 313"), struct('n', 1, 'code', "S 314"), ...
        struct('n', Inf, 'code', "S 315")};
    cfg.paradigms.myParadigm.triggerfix.phase_strategy = "trigger_only";

Choose phase_strategy when using phase starts. "trigger_only" skips a run when
phase QA fails. "block_only" counts blocks within observed boundaries without
phase QA. The default "trigger_then_block_fallback" tries phase QA and uses
block counting within observed boundaries on failure. With
trigger_phase_min_start_markers = [], QA requires each configured start marker.
A numeric value counts all observed occurrences. For a single phase using QA,
set trigger_phase_min_phases_with_remaps to 1 and trigger_phase_max_phase_share
to 1. The other QA limits are listed in the config.

To replace selected early trials after phased remapping, enable
enable_first_match_replacements and add first_match_replacements entries with
match_code, replace_code and optionally max_replacements (default 1). The
match_code_key and replace_code_key options look up codes in raw_triggers. Use
a replacement code outside the Step 06 epoch list to exclude the trial from
epoching.
The old triggerfix.rules option raises a configuration error.

For RTGMN/CF-style behavior logs, the optional run_raw_order_qc compares raw
trigger order against the log. Configure behavior_log_map, the log columns and
the tokens to compare. Set run_raw_order_qc to false if you only need renaming.
Run a representative subject and check the log and output event labels before
running the batch.

------------------------------
STEP 03: UNTIL ICA --> main preprocessing step: filters, detects and interpolates bad channels in preparation for ICA
- set start/stop trigger names, if data is to be cropped (not done by default)
- make sure that your AUX/EOG channel labels are listed correctly (though not case-sensitive), otherwise they might be interpreted as EEG data, which will mess up your ICA
- high-/lowpass filter Settings are highly dependent on your Research Question and Analysis Parameters, e.g. ERP vs. time-frequency, etc.; therefore our defaults are not prescriptive

Defaults:
- downsampling frequency: 250Hz, Note: Sampling rate needs to be at least 4 times the low-pass filter cutoff frequency, otherwise aliasing can occur
- Highpass filter: 0.1Hz
- Lowpass filter: 40Hz
- automatic bad channel detection: channel variance/z-score > 2.5, flatline ≥ 5 s or channel correlation < 0.80; spherical interpolation before ICA for EEG-channels, dead/invalid AUX channels are removed
- linenoise removal via cleanline (EEGLab)
- epoch rejection via ERPLab: exclude voltage over 300uV, sample-to-sample voltage jumps over 75, flatlines (within 0.5uV) of over 200ms

STEP 04: ICA
- choose ICA method (currently only one Option)

------------------------------
STEP 05: AFTER ICA / ICLABEL:
- set ICLabel thresholds (https://labeling.ucsd.edu/tutorial)
- decide which summary tables you want as output (still work in progress as of May 2026)

STEP 06: EPOCHING + FINAL ARTIFACT REJECTION:
- choose one of two modes for epoching: baseline or event-locked
	event-locked:
	- if you have task data and want to cut epochs based on event-triggers

	baseline:
	- for continuous recording of baseline/resting-state data
	- assumes alternating eyes open and eyes closed phases;
